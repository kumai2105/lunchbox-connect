### 5.2 Live smoke (read-only, from a GitHub runner)

The authoring sandbox cannot reach `*.supabase.co` — the network policy
answers 403 to CONNECT, confirmed against the proxy's own status endpoint — so
"the live boundary holds" is asserted from a runner that can reach it. Every
request in that workflow is a GET; nothing it does writes.

It asserts: the Worker serves the built SPA shell; deep links fall back to it;
the shipped bundle references the **production** Supabase project and contains
no `service_role` material; Supabase Auth answers; an anonymous holder of the
public anon key is refused on `institutions`, `v_dashboard_institutions`,
`students`, `serving_records`, `app_users`, `student_parents`, `classes`,
`meal_services`, `serving_record_note_archive` and all three analytics views;
and `admin-create-user` refuses a caller with no JWT.

A probe that answers **HTTP 400 fails the job**. PostgreSQL resolves column
names during parse, before it checks privileges, so a 400 means the request
never reached the authorization boundary and proved nothing about it. The
first run of this smoke failed exactly that way on two probes where I had
named columns by hand and got them wrong; the probes now use `select=*`.

## 6. The defect found during this release

`v_dashboard_institutions` carries no role test of its own. It is safe only
because `security_invoker = true` makes its base-table reads run as the
caller, so RLS scopes them. `0031` created it that way. `0033` rebuilt it to
fix a completion denominator and wrote `create or replace view ... as`,
omitting the `with (security_invoker = true)` clause.

**`CREATE OR REPLACE VIEW` resets reloptions when the clause is absent.** The
option was dropped silently — no error, no warning, and the view kept
returning the same rows to an admin, so nothing looked wrong. It had reverted
to owner rights, and every base-table read inside it ran as `postgres`.

`anon` holds `SELECT` on that view, so the exposure was **unauthenticated**.
Reproduced against production before the fix was written: as `anon`,
`select * from institutions` was refused, while
`select name, classrooms, active_students from v_dashboard_institutions`
returned every institution's name, classroom count and eligible-child
headcount. **No child-level data was reachable**; tenant identity and
headcount were.

Fixed by migration `0039`, which restores the option on that view and sets it
on the three analytics views for defence in depth. Recorded as **Decision 036**
in `13_DECISION_LOG.md` so the next rebuild of one of these views restates the
clause rather than rediscovering this.

Post-fix, as `anon`, against the live public REST endpoint: all four views
answer `401`. The dashboard view now refuses with `permission denied for table
institutions` — the caller's own privileges, which is exactly what
`security_invoker` restores.

## 7. Open items — flagged, not blocking, not invented

1. **Leaked-password protection is disabled** in Supabase Auth. Enabling it
   checks new passwords against HaveIBeenPwned. This is a console setting, and
   turning it on changes the sign-up/reset experience for real users, so it is
   the Founder's call, not a silent change made during a release.
2. **86 WARN advisors, 0 ERROR.** The bulk are one linter category —
   `*_security_definer_function_executable` — covering the `app_*` predicates
   that RLS policies must be able to call, and the `guard_*` trigger functions,
   which return `trigger` and therefore cannot be invoked through PostgREST at
   all. Three legacy functions (`touch_updated_at`, `set_updated_at`,
   `app_is_api_client`) have a mutable `search_path`. None is an exposure; none
   was changed here.
3. **An *Absent* child's roster badge renders the same green check** as a child
   who ate. This is a presentation decision and visual work is frozen, so it is
   reported rather than changed.
4. **The platform is live but not yet operating.** `meal_services` is empty and
   `institution_rotation_assignments` has no rows, by design — which menu an
   institution uses and which periods it is contracted for are business
   agreements the Admin configures through the software, never inferred by a
   migration. Until an Admin assigns a rotation and publishes, the Classroom,
   Kitchen and Parent screens have nothing dated to show. That is the correct
   empty state, not a defect.

Everything previously marked `BLOCKED_BY_SPEC` is unchanged and was not
invented: meal-performance classification thresholds, a mandatory low-intake
reason, retention/deletion/archive policy, guardian unlink semantics,
Packing/Dispatch/Delivery, multi-kitchen routing, per-institution timezones.
