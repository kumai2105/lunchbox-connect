# Recovery point before applying 0042 — production `llnofriwvnerntrbpehc`

Captured 2026-08-22 from the live database, immediately before `0042` was
applied. Stored in the repository rather than in an ephemeral runner, so it
survives this session.

`0042` is grant-only. Its exact inverse is stated below, so this file is a
complete rollback for the change — not a database dump, and not a substitute
for one. Supabase's managed backup/PITR state for this project is not exposed
by the MCP tools available here and was NOT verified.

## State before the change

| Object | `authenticated` | `anon` |
|---|---|---|
| `audit_log` | DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE | *(none)* |
| `v_dashboard_institutions` | DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE | DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE |

`v_dashboard_institutions` has `security_invoker = true`.
`audit_log` has 1 policy (`audit_log_select`, Super Admin only).

## What this tells us, checked rather than assumed

1. **The `authenticated` half of 0042 is a NO-OP on production.** Both objects
   already carried SELECT through Supabase's platform default privileges. The
   `permission denied` failures reproduced during this closure were real on the
   local CLI stack only. This is the same pattern as finding 6, and this time
   it was checked before being claimed.

2. **The `anon` half is a real hardening.** `anon` held full grants on the
   dashboard view. `CREATE OR REPLACE VIEW` re-applies default privileges, and
   the view has been recreated four times (0006, 0023, 0031, 0033), so each
   recreation restored them.

   The exposure is currently **contained**, verified directly:

   ```
   set local role anon;
   select count(*) from public.v_dashboard_institutions;
   -- ERROR: 42501 permission denied for table institutions
   ```

   Because the view is `security_invoker`, the anonymous caller is stopped by
   the underlying table's own grants. That containment is a second layer, not
   the intended one — and migration 0031 did once make this very view
   `security_definer` (0039 reverted it), which is precisely the change that
   would have turned this into a live leak.

## Rollback

```sql
grant all on v_dashboard_institutions to anon;   -- restores the pre-0042 state
```

`audit_log` needs nothing: 0042 re-asserts a revoke that was already in effect.
